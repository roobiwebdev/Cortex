# Desktop recorder

Cortex ships a macOS screen, camera and audio recorder. The capture engine is Rec (rec-rs), imported with its history. The UI is a Tauri 2 app with a React front end that reuses `packages/ui`. This page covers how the pieces fit, where each concern lives, and the rules that differ from the web app.

## The layout

| Folder                      | Job                                                                                                        | May depend on                                                                    |
| --------------------------- | ---------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------- |
| `crates/rec-core`           | Platform-neutral settings schema, engine API (`RecorderEngine`, `EngineEvent`), state, settings store.     | serde, specta (optional). No Apple code.                                         |
| `crates/rec-engine-macos`   | Rec's capture, compose, encode, mixer and live code. Exposes `MacEngine`, which implements `rec_core`.     | rec-core, Apple frameworks                                                       |
| `crates/rec-macos-ui`       | Native window behaviour: live preview view, non-activating panels, capture exclusion, levels.              | Apple frameworks, raw-window-handle                                              |
| `crates/rec-engine-windows` | The Windows engine (`WindowsEngine`) and Win32 window helpers. Written, type-checked, not yet run.         | rec-core; on Windows the `windows` crate                                         |
| `crates/rec-cli`            | The `rec-rs` command-line recorder.                                                                        | rec-engine-macos                                                                 |
| `apps/desktop/src`          | React 19 + Vite + Tailwind 4 surfaces (main, settings, HUD, toasts, countdown, region picker, trim).       | `@starter/ui`, `@tauri-apps/api`                                                 |
| `apps/desktop/src-tauri`    | The Tauri shell (Rust crate `cortex-desktop`): windows, tray, IPC commands. `src/platform` is the OS seam. | rec-core; on macOS rec-engine-macos, rec-macos-ui; on Windows rec-engine-windows |
| `third_party/`              | Patched copies of upstream crates. See `third_party/README.md`.                                            |                                                                                  |

The Rust workspace is the root `Cargo.toml` (members `crates/*` and `apps/desktop/src-tauri`). The toolchain is pinned in `rust-toolchain.toml`. `.cargo/config.toml` sets `MACOSX_DEPLOYMENT_TARGET=15.0`, because the engine uses ScreenCaptureKit APIs from macOS 15. The pnpm workspace sees `apps/desktop` as the package `desktop`.

## Request flow

```
React surface (apps/desktop/src/surfaces/*)
   │
   ▼
lib/engine.ts                 useEngine(select?), level sources, connectEngine(). In a plain browser it is the mock engine.
   │
   ▼
ipc/bindings.ts               generated by tauri-specta. Typed commands and the engine://state event.
   │  invoke()
   ▼
Tauri command (src-tauri/src/ipc.rs)        the single IPC checkpoint
   capability allow-list (capabilities/default.json) → serde-typed input → validation
   │
   ▼
rec_core API                  RecorderEngine trait, RecorderSettings, EngineState, EngineEvent
   │
   ▼
MacEngine (rec-engine-macos)  state machine, pacer, compositor, writer, mixer
   │
   ▼
ScreenCaptureKit (screen, system audio) · AVFoundation (camera, mic, file writer) · VideoToolbox (H.264/HEVC)
```

Events travel back the same way. The engine calls its `EventSink`, the shell broadcasts `engine://state`, and `lib/engine.ts` updates the store that `useEngine()` reads.

Video frames never enter the webview. The preview is a native view under a transparent region of the window, so the webview only carries state, settings and levels.

The shell runs the platform's engine (`MacEngine` on macOS) through `src-tauri/src/shell.rs`, which gets it from `src-tauri/src/platform`. Every call into macOS code goes through that module; see [Platforms](platforms.md).

## Live preview

```
MacEngine preview session ──(CVPixelBuffer, ≤30 fps, scaled to the view)──▶ PreviewView sink
                                                                             │
NSWindow (main) ─ contentView ─┬─ PreviewView (AVSampleBufferDisplayLayer, below)
                               └─ WKWebView (drawsBackground = NO, page has a hole)
```

- **Native side.** `src-tauri/src/preview.rs` (`LivePreview`) attaches `rec_macos_ui::PreviewView` to the main window at setup, makes the webview transparent (`make_window_webviews_transparent`) and connects `PreviewView::sink()` to `MacEngine::set_preview_sink`. Both `rec-macos-ui` entry points take a window handle, so the shell has no `unsafe`.
- **Commands.** `set_preview_rect(x, y, w, h, radius)` places the view (CSS px from the webview's top-left) and tells the engine the view's pixel size. `set_preview_enabled(bool)` says whether the page shows the hole. Only the main window may call them (`capabilities/preview.json`).
- **When it runs.** The engine's preview session runs while the hole is shown and the window is visible. Visibility comes from the window's occlusion state, so hiding, minimising, covering the window or moving to another Space stops it. Rec's rule still holds: the replay buffer and streaming keep the engine capturing without a preview. The decision is `should_preview` in `preview.rs` (unit-tested). `CORTEX_DEBUG_PREVIEW_STATS=1` prints each on/off decision with its reason, and 0 fps while the preview is stopped.
- **Events.** Each window is its own WebKit process. `lib/engine.ts` listens per window, the shell sends level events only to visible windows, and progress-only state reaches hidden windows once a second. A hidden page stores that state and renders it only when it is shown again (`lib/visibility.ts`).
- **Render cost.** A visible webview should stay still while recording. Levels (about 30 a second) go to their own store in `lib/engine.ts` (`micLevels`, `systemLevels`), and `LevelMeter` given a `source` toggles segment attributes on an animation frame, with no React render. State events keep the previous object for fields whose content did not change. Window roots use `useEngineCalm()`, which ignores the progress counters, and the clock, bytes, dropped frames and free disk render from the leaves in `components/progress-text.tsx` once a second. Use `useEngine(select, isEqual)` for new views instead of reading the whole state. Avoid `backdrop-filter` and large repainting effects over the preview hole.
- **Frame size and rate.** The writer sends at most 30 preview frames a second. The engine scales each one with Rec's Metal Lanczos scaler (`FrameScaler`) to the view's pixel size, at most 1920 wide, before the sink. Low-power preview halves the rate to 15.
- **React side.** In the Tauri main window `PreviewStage` renders an empty box instead of `MockScreen` and reports its rect through `useNativePreviewHole` (`lib/native-preview.ts`): ResizeObserver, window resize and display scale changes. Nothing above the native view may paint, so `html[data-preview-hole]` makes html, body and the window roots transparent; the hole's box-shadow paints the dark stage around it, and a fixed backdrop behind everything paints the page around the stage. The camera overlay stays a React drag handle above the video (the engine draws the camera itself). The browser harness still renders `MockScreen`.
- **Own windows stay out of recordings.** The shell calls `rec_engine::screen::require_self_exclusion(true)`. If ScreenCaptureKit doesn't list the app, the engine looks once more after refreshing and then fails the capture with a clear error, rather than recording our own windows. The CLI leaves it off: it has no windows.

### Perf and self-test hooks

The shell reads these at launch (never set in normal use): `CORTEX_DEBUG_DATA_DIR` (settings folder), `CORTEX_DEBUG_TEST_PATTERN=1` (record Rec's test pattern, no Screen Recording grant needed), `CORTEX_DEBUG_RECORD_SECS=N` (record N s after launch, print the path, quit), `CORTEX_DEBUG_HIDE_MAIN=1`, `CORTEX_DEBUG_FRONT=1` (keep the main window on top and on every Space, full-screen ones included, so the preview keeps running; a Space switch or Mission Control by someone at the Mac otherwise stops it, which is what cut short idle perf runs), `CORTEX_DEBUG_PREVIEW_STATS=1` (print the preview frame rate) `CORTEX_DEBUG_TARGET=display:N|window:ID-or-text|app:BUNDLE_ID|region:N,X,Y,W,H` (what to capture, in points; applied only together with `CORTEX_DEBUG_DATA_DIR`, so the user's settings are never changed) `CORTEX_DEBUG_UPDATE_URL` (+ `CORTEX_DEBUG_UPDATE_INSTALL=1`; check a feed on 127.0.0.1 or localhost at launch, and install what it finds; see [Releasing](#releasing)) and, in debug builds, `CORTEX_DEBUG_OPEN=menubar|region|settings|onboarding|trim` (open that window 2 s after launch), and `CORTEX_DEBUG_LIVE_URL` with optional `_KEY` and `_SECS` (go live to a local test server through the IPC commands, store and then remove the key, print the stream states, quit; see `src-tauri/src/debug_live.rs`). `scripts/desktop/perf-compare.sh` uses them to compare CPU, memory and frame counts with Rec.app's `rec-rs record --test-pattern`, and marks an idle preview-on run invalid when any 5 s preview window drops under 29 fps.

## Capture targets

`rec_core::settings::CaptureTarget` says what is recorded. The engine turns it into Rec's `record` arguments (`engine::rec_settings_for`), so the GUI and the `rec-rs` CLI share one path, and the target is part of the capture key: a new area or app restarts the preview on it.

| Target    | ScreenCaptureKit filter                                                                         | CLI                     |
| --------- | ----------------------------------------------------------------------------------------------- | ----------------------- |
| `display` | `initWithDisplay:excludingApplications:` (our app)                                              | `--display N`           |
| `region`  | the display filter plus `sourceRect`                                                            | `--region X,Y,W,H`      |
| `window`  | `initWithDesktopIndependentWindow:`                                                             | `--window ID\|text`     |
| `app`     | `initWithDisplay:includingApplications:[app]` on the display holding the app's frontmost window | `--app BUNDLE_ID\|name` |

- **Units.** A region is in **points** from its display's top-left, as `sourceRect` takes it. `Display.width/height` are pixels, `Display.frame` is the display's place on the desktop in points, and `Display.scale` is pixels per point. `CaptureWindow.frame` is in points from the top-left of `CaptureWindow.displayId`. The region picker and the Area tab show pixels (points × scale), which is what gets recorded, and convert back to points when they save (`toPixels` / `toPoints` in `region-picker/geometry.ts`).
- **Output size.** The source's pixels (region × scale, the window at its display's scale, the whole display for an app) go through `rec_core::output::output_size`; see [Resolution and bitrate](#resolution-and-bitrate). A region is clipped to its display.
- **Our windows never appear.** Display and region capture exclude our app; app capture includes only the chosen app, and `screen::find_app` refuses this process; the window list (`screen::windows`) leaves our windows out, so they can't be picked as a window either.
- **App capture** records every window of the app on that display, including windows it opens later. The rest of the frame is black.
- **Icons.** `app_icon(bundleId)` returns a 64 px PNG `data:` URL (cached by bundle ID); `useAppIcon` in `lib/app-icons.ts` loads it. Icons stay out of the engine state so state events stay small.
- **Region picker.** The overlay covers the whole display under the cursor (sized in that display's points) and finds its display from its own screen position. Each time it is shown it re-lists windows, starts from the saved area on that display or the last one remembered for it (`settings.lastRegions`, kept by `validate` while `rememberRegion` is on), and snaps to real window frames. Clicking a window in Area mode sets the area to the window's frame; Window mode records the window itself. Enter or the button saves the target and closes the overlay; Esc cancels.

## Resolution and bitrate

`crates/rec-core/src/output.rs` decides the recorded frame size, the codec Auto becomes and the automatic bitrate. The engine uses it through `args::prepare`; `apps/desktop/src/lib/output-size.ts` mirrors it for the pickers. Both are tested against `crates/rec-core/tests/fixtures/output-sizes.json` (`cargo test -p rec-core`, `pnpm --filter desktop test`), so the UI shows the size the engine writes.

| Setting                 | Frame                                                                                             | 3456×2234 MacBook Pro display    |
| ----------------------- | ------------------------------------------------------------------------------------------------- | -------------------------------- |
| 720p / 1080p / 1440p    | Fitted inside 1280×720 / 1920×1080 / 2560×1440 (swapped for a portrait source). Never upscaled.   | 1114×720 / 1670×1080 / 2228×1440 |
| 4K (HEVC, Auto, ProRes) | 3840 on the long side at the source's shape, scaled up or down. Same as fitting inside 3840×3840. | 3840×2482                        |
| 4K (H.264)              | Fitted inside 3840×2160, never upscaled (the rule before 4K became 3840 wide).                    | 3342×2160                        |
| Native                  | The source's pixels, rounded down to even.                                                        | 3456×2234                        |

- **Examples.** A 4K monitor (3840×2160) is recorded as is. A 5K display gives 3840×2160. A 1080p display or a small region is upscaled to 3840 wide. A portrait window is 3840 tall (1080×1920 → 2160×3840). Output sizes are always even and keep the source's shape, so there are no bars.
- **Scaling.** Whenever the output differs from the source, ScreenCaptureKit delivers the source's own pixels and the Metal Lanczos scaler (`scale::FrameScaler`) resizes them, down or up (`record::capture_size`). ScreenCaptureKit's own scaling is softer (measurements in `scale.rs`).
- **Why H.264 keeps the old rule.** On the 3456×2234 MacBook Pro, real-screen recordings at 60 fps with the hardware H.264 encoder dropped frames at 3840×2482 (326 and 329 of 360) and at 3582×2314 (1137 and 1138 of 1200), and none at 3456×2234 or 3342×2160. HEVC kept every frame at 3840×2482. Auto picks HEVC above 1080p, so only an explicit H.264 choice gets the smaller frame, and the picker shows it.
- **Go live** is separate: `liveResolution` is a bounding box for the live encode (`args::live_box`) and does not use this rule.
- **Camera track** has its own size (`cameraResolution`, below) and uses the base bits-per-pixel rates.

**Automatic bitrate** = pixels × fps × bits per pixel, clamped to 1–400 Mb/s (`auto_bitrate`). A manual `bitrateMbps` replaces it. ProRes is fixed quality.

| Codec | Up to 1440p (≤ 2560×1440 pixels) | Above (4K-class, Native on Retina) |
| ----- | -------------------------------- | ---------------------------------- |
| HEVC  | 0.10                             | 0.14                               |
| H.264 | 0.16                             | 0.20                               |

That gives about 70 Mb/s HEVC or 100 Mb/s H.264 at 3840×2160 60 fps, 80 Mb/s HEVC at 3840×2482 60 fps, 65 Mb/s for Native on the MacBook Pro display, and half of each at 30 fps. Rec's 0.10 HEVC gave 42 Mb/s at 3342×2160 60 fps. Text on a 4K-class frame has finer strokes per pixel area than an upscaled 1080p frame would, and fast scrolling of dense text is where screen recordings smear first; the extra 40% (HEVC) and 25% (H.264) aims at that case. It is an average target, not a constant rate: a mostly still desktop encoded at 6 to 12 Mb/s in our 4K runs, so the higher rate costs file size only when the screen moves. 1440p and below keep Rec's rates.

## Recordings library and Quick trim

```
output folder ──scan──▶ trim::Library (src-tauri/src/trim.rs) ──recordings://changed──▶ lib/engine.ts (every window's `recordings`)
                              │
Trim window ── commands ──────┤  list_recordings · rename_recording · recording_thumbnails · recording_waveform · trim_recording · cancel_trim
            ── <video> ───────┘  cortex-media://localhost/<recording id>   (Trim window only, Range requests)
                              │
                              ▼
rec_engine::trim (AVFoundation)   inspect · thumbnails (JPEG) · waveform (peaks) · export (Fast/Exact) · trash
```

- **The list.** The shell scans the output folder for `.mov`/`.mp4` at launch, after each finished recording and after a trim or rename: newest first (file creation time), at most 200, hidden and unreadable files left out. While recording, files written in the last 4 s are skipped (the file in progress). Track details come from AVFoundation once per file (cached by inode, size and modification time). Ids are file stems, like the engine's; a stem shared by two files uses the file name. Once loaded, the scan replaces the engine's per-run `recordings` in `useEngine()`.
- **Ids, never paths.** Every command takes a recording id that must be in the latest scan. Rename takes a name, checked by `rec_core::library::validate_name` (no separators, `:`, control characters or leading dot), and keeps the folder and extension.
- **Timeline.** `recording_thumbnails` returns small JPEGs (192 px wide) as `data:` URLs and `recording_waveform` the peak level per slice of the played audio track. Both are cached in `~/Library/Caches/dev.roobi.cortex/{thumbs,waveforms}` (`<CORTEX_DEBUG_DATA_DIR>/Caches` in debug runs). The webview gets no file access for them.
- **Playback.** `cortex-media://localhost/<id>` (`trim::media_protocol`, registered in `lib.rs`) serves the scanned file with Range support, 4 MB per response, and only to the Trim window; anything else gets 403 or 404. The CSP allows it in `media-src` only. WKWebView plays H.264 and HEVC `.mov`/`.mp4` from it (checked with the test pattern). `usePlayback` drives the `<video>`; reverse shuttle (J) steps the position, since WebKit cannot play backwards.
- **Export.** `trim_recording(id, { startSecs, endSecs, mode, output, keep })`:
  - Fast: `AVMutableComposition` plus the passthrough preset. No re-encode; the cut starts at the keyframe before the in point and an edit list hides the extra frames, so Apple players start on the exact frame.
  - Exact: re-encoded with the HighestQuality preset (HEVC for HEVC sources). Frame-accurate in every player. The export session may reorder tracks (audio first).
  - Kept tracks follow the writer's layout (mix, system, mic; `rec_engine::trim::audio_plan`): the mix is kept only when both system and mic are, and when the mix is dropped the kept stems are enabled so the file still plays its audio. Later video tracks are the camera track.
  - Copy writes `<name>-trim.<ext>` (then `<name>-trim 2.<ext>`, ...) and never overwrites. Replace writes a hidden temporary file, moves the original to the Trash (`NSFileManager trashItemAtURL`, never deleted outright) and renames the new file to the original name.
  - Progress arrives as `trim://progress`; `cancel_trim` stops the export and removes the partial file. The new file is announced like a finished recording, so the toast and the menu bar list update.
- **Browser harness.** `surfaces/trim/native.ts` is `null` outside Tauri, and the Trim window keeps its simulated player, filmstrip and export.

## Windows are built on demand

Only the main window exists at launch. Every other window in `tauri.conf.json` (settings, onboarding, trim, menu bar panel, HUD, toasts, countdown, region picker) has `"create": false`. Each window is its own WebKit WebContent process (40 to 200 MB, plus CPU while it animates), so building them all at launch cost about 1 GB and, while recording, about 3% of a core per hidden window.

- **Build.** `windows::ensure(app, label)` returns the window, building it from its config entry first if needed. Every path that shows a window goes through it: `open_window` (settings, onboarding, trim; the webview can no longer find windows by label), `open_floating`, the tray click, and the engine-driven countdown, HUD and toasts. Floating windows get their native behaviour in `floating::on_created` before they are shown.
- **Destroy.** `windows::reap` runs every 5 s and destroys a lazy window that has been hidden for 30 s, so its WebContent process exits. It keeps the HUD and menu bar panel while recording, the countdown while it runs or while it is warm, and the toasts window until it has delivered what it holds.
- **Countdown latency.** A countdown window built when the countdown starts renders about 130 to 150 ms later (debug build). To avoid that delay, the countdown is built ahead of time whenever the main window gets focus and a countdown is set, and it stays warm while the main window is shown.
- **Toasts.** Toasts go through the shell, not straight to the toasts window, because that window may not exist yet. The floating observer turns `recording-finished`, `replay-saved` and `error` into toasts, other windows call `push_toast`, and the shell holds them until the toasts window calls `window_ready` after its first render. Every window calls `window_ready`, and the shell logs how long the window took from creation to that point.
- **Hidden pages idle.** `lib/visibility.ts` mirrors `document.hidden` onto `html[data-hidden]`, which pauses every CSS animation (`styles.css`), and `engine.ts` defers state renders until the page is visible. WebKit reports an ordered-out or fully covered window as hidden (checked with a debug probe: the countdown and HUD flip to `hidden` when the shell hides them and back when it shows them).

## Camera track

With **Save camera as separate track** on (`cameraTrack`, Settings → Camera) and a camera in the recording, the engine also records the raw camera (`rec record --camera-track file|sidecar`, `writer::CameraTrack`). The burned-in overlay stays in the main track either way.

- **Where it goes.** A `.mov` gets a second video track, in one alternate group with the main track (main is the default), so QuickTime and AVPlayer show the composite and editors see both. An `.mp4` gets a sidecar `<name>.camera.mov` next to it instead, because many editors ignore a second video track in MP4. `Recording.hasCameraTrack` is true only for the in-file track (an `.mp4`'s camera is in the sidecar).
- **Unmirrored.** The track holds the frames as the camera delivers them. Mirroring is a display choice applied by the compositor to the overlay only.
- **Timeline.** The pacer appends the newest camera frame on every main-track slot, with the main track's timestamp: CFR at the output fps, same start, same pause cuts, same end (`endSessionAtSourceTime` trims both). A 30 fps camera on a 60 fps grid repeats each frame, which costs almost nothing in H.264/HEVC. The sidecar starts its session at the same host time, so it lines up at 0 with the main file.
- **Encoding.** Same codec as the main track (ProRes main gives a ProRes camera track), at the camera's size, with a bitrate sized for 30 real frames (`writer::camera_video_spec`). Both files are fragmented every 2 s, so a crash leaves the camera playable up to the last fragment too.
- **Resolution.** `cameraResolution` (720p or 1080p) caps the capture format. `camera::pick_format` takes the largest device format at or under that height (24 fps or faster), so a 720p-only camera falls back to 720p. The frames are delivered at exactly that size, and a running camera is reused for a recording only when it was opened at the same cap (the preview reopens when the setting changes).
- **Camera-only scene.** The track is recorded there too: the scene can switch live, and the track keeps the camera's native size.
- **Cost.** Measured 2026-11-03 on the FaceTime HD camera at 1080p, test pattern at 1080p60 H.264, 20 s window: 50.3% CPU with the track, 48.2% without (about +2 points), and about 9.5 Mb/s more file. `writer::tests::camera_track_follows_the_main_timeline` checks length, frame count and pause cuts for both the .mov track and the .mp4 sidecar.

## Floating windows

The HUD, toasts, countdown, region picker and menu bar panel are built on demand (see above). `src-tauri/src/floating.rs` owns their behaviour:

- **Native panel behaviour.** When one is built, `rec_macos_ui::configure_floating_window` gives it its `FloatingKind` level (menu bar panel highest, then countdown and toasts, region picker, HUD), puts it on all Spaces and over full-screen apps, makes it non-activating (`_setPreventsActivation:` on tao's window) and sets `sharingType = none`. The countdown also ignores mouse clicks. The safe wrappers take the window handle, so the shell has no `unsafe`.
- **Driven by the engine.** Every outbound event passes through `floating::observer` before it reaches the webviews. The countdown window shows centred on the main display while the status is `countdown`. The HUD shows while recording or paused if `settings.showHud` is on, the user did not hide it, and the main window is not frontmost. Its bottom-centre is remembered per display in `hud-positions.json` (Application Support) and kept inside the visible area.
- **Toasts have one owner.** The toasts window builds the queue from `engine://recording-finished`, `engine://replay-saved` and `engine://error`, which the shell sends to it (and holds until it is ready). Other windows send their toasts (failed commands) through `push_toast`, which reaches it as `ui://toast`. It shows itself top-right under the menu bar on the display under the cursor, and hides when the queue is empty.
- **Sized to content.** In a window, a floating surface renders only its card (`useWindowed()` from `lib/floating.ts`). `FittedHost` in `app/tauri-window.tsx` measures it and calls `fit_floating`, which keeps the HUD's bottom-centre and the countdown's centre in place. The browser harness keeps the fake desktop layout.
- **Opening and closing.** `open_floating` places the menu bar panel under the status item and the region picker over the full display under the cursor (one overlay per display is still to do). `hide_floating` closes the calling window; the menu bar panel also closes on blur and Esc, the region picker on confirm or cancel. A hidden HUD comes back from the panel menu ("Show recording HUD") or on the next recording.
- **Global hotkeys** use Carbon (`rec_engine::hotkey`), which needs no Accessibility permission: ⇧⌘R starts, cancels the countdown, or stops; ⇧⌘S saves the replay and is registered only while the replay buffer is on; Esc is registered only during the countdown and cancels it.
- **Main window and quit.** Closing the main window hides it; the app stays in the menu bar and a Dock click reopens it. Quit finalizes an active recording and flushes settings before the process ends (`src-tauri/src/quit.rs`). An exit request (tray Quit, `AppHandle::exit`, the debug recording run, SIGTERM or SIGINT) is held back while a `quit` thread runs `Shell::shutdown`, then that thread exits, so the event loop keeps running while the file is written. ⌘Q from the app menu skips `ExitRequested`; `RunEvent::Exit` runs the same shutdown on the main thread. `MacEngine::shutdown` waits at most 500 ms for its ticker thread and then finalizes without it.

Screenshots cannot see these windows, because they are excluded from sharing. To check them, run a debug build with the test pattern:

```
CORTEX_DEBUG_TEST_PATTERN=1 CORTEX_DEBUG_RECORD_SECS=6 CORTEX_DEBUG_HIDE_MAIN=1 CORTEX_DEBUG_CAPTURABLE=1 \
  target/debug/bundle/macos/Cortex.app/Contents/MacOS/cortex-desktop
```

It keeps its settings and recordings in a temporary folder, starts one recording with a 3 s countdown, and with `CORTEX_DEBUG_CAPTURABLE=1` lets `screencapture` see the floating windows. Release builds ignore these variables.

## First-run tour and coach marks

The onboarding window (880×560, `AppWindow::Onboarding`) is a nine-step tour: welcome, permissions, what to record, camera, the record shortcut, files, Quick trim, replay and live, done. The left half is an animated stage (`surfaces/onboarding/stage.tsx`), the right half has a kicker, headline, lede and the real control for the step (`panels.tsx`). Enter and → go forward, ← goes back, the dot pager jumps back to a step already passed.

- **When it opens.** At launch while `settings.onboardingCompleted` is false (`tour::open_on_first_run`, skipped in debug recording runs and with `CORTEX_DEBUG_HIDE_MAIN`), from Help › Show the Tour (`tour::app_menu`, Tauri's default menu plus one item) and from Settings › General. Finishing, Skip tour and closing the window (`WindowEvent::CloseRequested` in `tour.rs`) all store `onboardingCompleted = true`. Settings version 2 counts every version 1 file as onboarded, so existing users never see it at launch.
- **Gate.** Only the macOS Screen Recording grant blocks Continue (`gatedPermission` in `steps.ts`). Camera and microphone can be skipped. The step index is kept in `localStorage` until the tour is done, so a relaunch for Screen Recording comes back to the same step.
- **Per platform.** `rec_core::Platform::current()` reaches the UI through the `platform` command (`lib/platform.ts`, read before the first render). All copy and platform facts (permission rows, shortcut keys, default folder, key store) live in one typed table, `PLATFORM_FACTS` / `TOUR_COPY` in `surfaces/onboarding/steps.ts`. On Windows the permissions step is the camera and microphone privacy switches with no gate; on Linux it explains the screen-sharing portal. The browser harness switches platform from the sidebar or `?platform=windows|linux` (`?clean` hides the review controls for screenshots).
- **Shortcut practice.** The Carbon hotkey never reaches the webview. While the shortcut step is on screen the tour calls `set_hotkey_practice(true)` (onboarding window only, `capabilities/onboarding.json`), and ⇧⌘R is sent to it as `tour://hotkey-pressed` instead of starting a recording, provided nothing is recording and the window is visible (`tour::catch_record_hotkey`). Practice is switched off when the step changes and when the window closes.
- **Sound.** `lib/sounds.ts` synthesizes a soft blip per step with Web Audio (no audio files). It plays only when `settings.sounds` is on and the engine is idle.
- **Motion.** Scenes enter in 0.3 s, mocks in 0.5 s (`tour-*` classes in `src/styles.css`, colours from studio tokens). Reduce Motion stops them through the rule in `studio.css` and leaves each end frame.
- **Coach marks.** `components/coach-mark.tsx` shows a small tip the first time someone draws an area (region picker), opens Quick trim and opens Go live. Dismissed hints are stored in `settings.seenHints` (`rec_core::settings::CoachHint`); Settings › General › Show tips again clears them.

## Permissions

macOS privacy grants (TCC) are read and requested by `rec_engine::tcc`. The app never runs `tccutil reset` (that wiped grants the user had given) and never re-launches its own executable to ask; both stay in the `rec` CLI's `permissions --request` path only.

- **Run with what is granted.** `rec_core::sources::plan_sources` decides per source from the scene, the mic switch and the grants. A missing camera or microphone grant drops that source from the preview and recordings; it does not stop them. Only a source the scene cannot do without blocks it: the screen for Screen and Screen + Camera, the camera for Camera only. The camera-only scene runs without a Screen Recording grant (the camera's frames drive the clock, and the mic uses AVCapture). The CLI keeps its strict check (`record::check_permissions`).
- **Say what is missing.** The preview shows "Camera needs permission · Allow" where the overlay goes and "Microphone needs permission · Allow" in the mixer strip. Empty camera and mic menus offer "Allow camera access…" / "Allow microphone access…". Allow shows the system prompt when macOS has never asked, and opens System Settings otherwise (macOS asks only once).
- **Starting a recording** asks first for an undecided microphone (and camera, in camera scenes), waiting for the answer. A source that stays missing is left out, with a warning toast.
- **`request_permission`** shows the prompt for camera and microphone (`requestAccessForMediaType`, answered off the main thread) and calls `CGRequestScreenCaptureAccess` for the screen, which lists Cortex in System Settings. It returns the resulting state.
- **`check_permissions`** is cheap and polled once a second by onboarding. A running process keeps the Screen Recording answer it had at launch, so when this process still sees no grant, the command asks a new process of the same app (`cortex-desktop --cortex-screen-preflight`). If that one sees the grant, `screenNeedsRelaunch` is set and onboarding shows **Reopen Cortex** (`relaunch`, refused while recording).
- The engine re-reads grants about once a second. A change re-lists cameras and mics and rebuilds the preview, so a grant takes effect without a restart. Devices are also listed on the engine's first tick.
- Usage strings (`NSCameraUsageDescription`, `NSMicrophoneUsageDescription`, `NSScreenCaptureUsageDescription`) live in `src-tauri/Info.plist` and must be in the built bundle, or macOS refuses to prompt.

To check the missing-permission paths on a Mac where everything is granted, set `CORTEX_DEBUG_WITHHOLD=camera,microphone` (grants then read as never asked). Launch test builds with `open -n -a <app> --env ... --stdout <log> --stderr <log>`: run straight from a terminal, macOS charges TCC to the terminal app and the grants you see are the terminal's.

## Dev signing identity

macOS ties Screen Recording, Camera and Microphone grants (TCC) to the app's code signature. An ad-hoc signature changes on every build, so each rebuild looks like a new app and macOS asks again. A stable self-signed certificate keeps the grants across rebuilds.

This Mac has a self-signed code-signing certificate called **Cortex Dev Signing** in the login keychain. Sign local builds with it:

```
APPLE_SIGNING_IDENTITY="Cortex Dev Signing" pnpm --filter desktop tauri build --debug
```

To create one on another Mac, open Keychain Access, choose Certificate Assistant, Create a Certificate, and pick type "Code Signing". `security find-identity -p codesigning` should then list it. It shows as not trusted, which is fine for local signing.

Until the Apple Developer membership exists, releases are signed with this identity too (see [Releasing](#releasing)). It cannot pass Gatekeeper on another machine: people who install it have to allow it once in System Settings → Privacy & Security. Never commit the certificate or its private key, never export it, and never put it in CI.

## Releasing

Verified on 2026-11-03 (Apple Silicon, macOS 27): 0.1.0 and 0.1.1 built with the script; a copy of 0.1.0 installed from its DMG into a scratch folder updated itself from a local feed to 0.1.1 and relaunched; the updated app kept the designated requirement `identifier "dev.roobi.cortex" and certificate leaf = H"b3e0…"`, still saw Screen Recording, Camera and Microphone as granted, and recorded both the test pattern and the real screen (3 s, 180 frames at 60 fps). A bundle re-packed after signing (signature check failed), a feed announcing 0.1.2 for the 0.1.1 bundle (signed-version check failed) and an install during a countdown (refused) all left 0.1.0 in place. Not yet seen: the DMG window as Finder draws it, notarization, and an update over real HTTPS.

`scripts/desktop/release-macos.sh` builds a release into `dist/desktop/<version>/` (gitignored). It never uploads anything.

### Steps

1. Set the version: `scripts/desktop/bump-version.sh 0.1.1`. It writes `tauri.conf.json`, `apps/desktop/package.json`, `src-tauri/Cargo.toml` and the `cortex-desktop` entry in `Cargo.lock`. `cargo test -p cortex-desktop` fails if they disagree. The UI reads the version from `tauri.conf.json` at build time (`vite.config.ts`).
2. Commit, then run `scripts/desktop/release-macos.sh --notes "What changed"` (or `--notes-file FILE`). It:
   - cleans the bundle folder, the web build and the `cortex-desktop` crate, then runs `tauri build --bundles app` with updater artifacts on (the app and its `.app.tar.gz` + `.sig`);
   - signs with `CORTEX_SIGNING_IDENTITY` (default `Cortex Dev Signing`), hardened runtime, `Entitlements.plist`;
   - checks the signature, the `Info.plist` version, and that the designated requirement names this certificate;
   - builds the DMG with `dmgbuild` and signs it;
   - checks the DMG: it verifies, mounts, holds `Cortex.app` and an `Applications` link, and the app's signature still verifies after copying it out;
   - checks that the updater signature carries the version (`requireSignedVersion`);
   - notarizes and staples when Apple credentials are set (below);
   - writes the release folder and unregisters the build's `Cortex.app` from Launch Services.
3. Publish by hand once hosting exists: put the folder's files at `<base>/<version>/`, then replace `<base>/latest.json` with the new `latest.json`. Installed apps pick it up within a day (or at once with Check now).

The release folder:

| File                                      | What it is                                                                                |
| ----------------------------------------- | ----------------------------------------------------------------------------------------- |
| `Cortex_<version>_aarch64.dmg`            | The installer: the app and an Applications link on a light background.                    |
| `Cortex_<version>_aarch64.app.tar.gz`     | The updater bundle: the signed `Cortex.app`, tarred.                                      |
| `Cortex_<version>_aarch64.app.tar.gz.sig` | Its minisign signature from the updater key.                                              |
| `latest.json`                             | The update manifest: version, notes, date, and per platform the bundle URL and signature. |
| `SHA256SUMS`                              | SHA-256 of every file above.                                                              |
| `BUILD.txt`                               | Commit, identity, designated requirement, whether it was notarized.                       |

Builds are Apple Silicon only (`darwin-aarch64`). Intel Macs would need `tauri build --target universal-apple-darwin` and a `darwin-x86_64` entry in `latest.json`; the script does not do that yet.

The DMG window is 660×400 with the app at (180, 200) and Applications at (480, 200) over `src-tauri/dmg/background.png` and `background@2x.png` (brand teal arrow and caption), set in `src-tauri/dmg/dmgbuild-settings.py`. The script builds it with [dmgbuild](https://github.com/dmgbuild/dmgbuild) (MIT, pinned to 1.6.7, installed into `~/.cache/cortex/dmgbuild-venv` on first use), which writes the window layout itself. Tauri's own DMG step scripts Finder over AppleEvents instead; that needs an Automation grant and a GUI session, and it timed out when run from an agent, so `tauri.conf.json` bundles only the app.

| Secret                | Where                                                                                   | Used for                        |
| --------------------- | --------------------------------------------------------------------------------------- | ------------------------------- |
| Updater private key   | `~/.config/cortex/updater.key` (mode 600, folder 700). Never in the repo.               | Signing update bundles          |

**Back up `~/.config/cortex/updater.key` and its password now**, together, somewhere safe off this Mac (a password manager entry with the file attached works). Read the password with `security find-generic-password -s cortex-updater-key -w`. Every installed copy of Cortex trusts only this key. If it is lost, no update can ever reach those copies again: users would have to download a new DMG by hand. If it leaks, someone with access to the feed URL could ship them anything, so keep it off shared drives and out of CI logs. To use it on another Mac, copy the file to the same path and add the Keychain item, or set `CORTEX_UPDATER_KEY` and `TAURI_SIGNING_PRIVATE_KEY_PASSWORD`.

Back up the `Cortex Dev Signing` certificate too (Keychain Access → export as .p12 with a password, stored with the key). Its hash is in the designated requirement, `identifier "dev.roobi.cortex" and certificate leaf = H"b3e0…"`. macOS ties Screen Recording, Camera and Microphone grants to that requirement, so as long as every release is signed with the same certificate, updates keep the grants. A new self-signed certificate (or ad-hoc signing, which changes the requirement on every build) means every user grants Screen Recording again after the update.

### How updates work in the app

- **Feed and check.** `tauri-plugin-updater` asks the endpoint for `latest.json` and offers the entry for `darwin-aarch64` if its version is newer. It is driven from Rust only (`src-tauri/src/updater.rs`): the webview has three commands, `update_status`, `check_for_updates` and `install_update`, granted to the Settings and menu bar windows (`capabilities/updates.json`). No window gets the updater or process plugin's own permissions, so a page can only ask for the one update the feed announces.
- **Signatures.** The bundle must verify against the public key in `tauri.conf.json`, or it is never installed. `requireSignedVersion` also checks that the signature names the announced version, so a tampered feed can't relabel an older signed bundle as new.
- **Never during a recording.** `Shell::begin_update` refuses the install while recording, paused, counting down, finalizing or live, and holds `start` and `go_live` off from then until the relaunch. A bundle that finishes downloading during a recording is kept; the button installs it later.
- **Relaunch.** After installing, the app quits through the normal quit flow (finalize, flush settings) and `RunEvent::Exit` reopens it with `open -n`. Relaunching through Launch Services gives the new process its own launchd parent, as Tauri's restart does; unlike it, the `CORTEX_DEBUG_*` variables are passed on so test copies keep their scratch data folder.
- **Quiet check.** While **Check for updates automatically** (`autoUpdate`) is on, the shell checks 20 s after launch and then hourly whenever the last attempt is a day old (`update-check.json` next to the settings). It only finds updates; installing always waits for a click in Settings → General (or the menu bar's **Update to Cortex x.y.z…**, which opens it).
- **UI.** `lib/updates.ts` keeps the status from `updater://status` (checking, available version and notes, download progress, ready, installing, last error). Settings → General shows it in the Updates group; About shows the version.

### Notarization: when the Apple Developer membership arrives

Nothing in the code changes. In order:

1. In the Apple Developer portal, create a **Developer ID Application** certificate (Certificates → +). Make the CSR in Keychain Access on this Mac so the private key lands in the login keychain. `security find-identity -p codesigning -v` should then list `Developer ID Application: <Name> (<TEAMID>)`.
2. Create notarization credentials, either an app-specific password at account.apple.com (Sign-In and Security → App-Specific Passwords) for your Apple ID, or an App Store Connect API key (Users and Access → Integrations → Keys, "Developer" access; download the `.p8` once).
3. Build with:

   ```
   CORTEX_SIGNING_IDENTITY="Developer ID Application: <Name> (<TEAMID>)" \
   APPLE_ID=<apple id email> APPLE_PASSWORD=<app-specific password> APPLE_TEAM_ID=<TEAMID> \
     scripts/desktop/release-macos.sh --notes "..."
   ```

   or with `APPLE_API_KEY=<key id> APPLE_API_ISSUER=<issuer uuid> APPLE_API_KEY_PATH=<path to .p8>` instead of the three `APPLE_*` values. Keep these in the Keychain or a password manager and export them only for the run. The Tauri bundler then notarizes and staples the app before it builds the DMG and the updater bundle; the script signs, notarizes and staples the DMG, and checks it with `spctl`. A half-set group of `APPLE_*` variables stops the script, and notarization refuses any identity that isn't Developer ID.

4. Check on a clean Mac (or a new user account) that the downloaded DMG opens without the "unidentified developer" prompt.

What users see: the Developer ID certificate has a different hash, so the designated requirement becomes `anchor apple generic and identifier "dev.roobi.cortex" and certificate leaf[subject.OU] = "<TEAMID>" …`. The first update from a `Cortex Dev Signing` build to a Developer ID build therefore looks like a new app to macOS, and **users grant Screen Recording (and Camera, Microphone) once more**. Say so in that release's notes. Later Developer ID releases keep the grants, because the requirement names the team, not one certificate. The updater key stays the same, so those installs still update.

## Security rules for the desktop app

There is no server in the recorder yet, so the tRPC procedure builder does not apply. These rules take its place:

- **One IPC checkpoint.** Every webview call is a command in `src-tauri/src/ipc.rs`. Each window gets only the commands its capability lists. No shell, fs, http or other plugin is enabled for the webview.
- **Validate in Rust.** Commands take serde types from `rec-core`. Rust checks ranges, enums and paths before the engine sees them. Settings forms in React also validate with Zod, as on the web.
- **No secrets over IPC.** Stream keys live in the macOS Keychain. The webview can set or remove a key but only ever reads back a `keyStored` flag. Never log a key.
- **No remote content.** The CSP in `tauri.conf.json` allows only `'self'`, IPC, and `blob:`/`data:` media. Fonts and assets are bundled. Do not add CDN URLs or `withGlobalTauri`.
- **Writes stay in the output folder.** The engine writes recordings only under the chosen output directory, and the settings store only under the app's Application Support folder. Trim and rename write only next to the recording they act on; Replace moves the original to the Trash.
- **Media by id.** The webview reads recordings only through `cortex-media://`, which serves files from the latest output-folder scan to the Trim window. There is no asset protocol or fs scope.
- **Updates are signed and driven from Rust.** The webview can read the update status, check, and install the one update the feed announced; it gets no updater or process plugin permission. A bundle installs only with a valid signature from our key that names its version. See [Releasing](#releasing).
- **Minimal entitlements.** `Entitlements.plist` grants camera and audio input only. Add one only with a stated reason.
- **Hidden from recordings.** HUD, toasts, countdown, the region picker and the menu bar panel must never appear in a capture. The engine's `SCContentFilter` excludes the whole app, and `rec-macos-ui` sets `sharingType = none` so other apps' screenshots miss them too.

## Rust rules

- No new `unsafe` outside `rec-engine-macos`, `rec-macos-ui` and `rec-engine-windows`. Every `unsafe` block has a `// SAFETY:` comment that says why the call is sound.
- New crates must pass `cargo fmt --check` and `cargo clippy -- -D warnings`. CI enforces this for `rec-core` and `cortex-desktop`. The imported Rec crates keep their upstream style for now, so subtree pulls stay clean.
- **Never block on the main thread from engine or background threads.** Engine events reach `ipc::emitter` and `floating::observer` on the engine's ticker and writer threads, and at quit the main thread waits for those threads. Any `WebviewWindow` getter (`is_visible`, `outer_position`, `scale_factor`, ...) or `run_on_main` from `rec_macos_ui` called off the main thread waits for the main thread: that deadlocked quit. From those threads, read cached state (`ipc::VisibleWindows`) and hand window work to `AppHandle::run_on_main_thread` without waiting for it. The same applies to anything the main thread may join.
- Errors cross IPC as `rec_core::EngineError`, never as panics. Do not `unwrap()` on input that came from the webview.
- The TypeScript rules in `CLAUDE.md` still apply to `apps/desktop/src`.

## Testing

- **Rust unit tests.** `cargo test --workspace`. `rec-core` covers the state machine, settings migration and the store. The imported engine keeps Rec's tests.
- **Quit regressions.** `ipc::tests` reproduces the quit deadlock in miniature (a wait on the main thread from the ticker while the main thread joins it) and checks the visibility registry gets through. `crates/rec-engine-macos/tests/shutdown_blocked_sink.rs` holds the ticker inside the event sink and requires `shutdown` to return and leave a playable file.
- **Quick trim.** `crates/rec-engine-macos/tests/trim_test_pattern.rs` records 6 s of the test pattern and trims 1.0 to 4.0 s. Exact must be 3.0 s ± 1 frame (180 frames); Fast must keep the same streams and codecs, with video packets that are a byte-identical run of the source's (no re-encode), and AVFoundation must report 3.0 s. It also checks thumbnails, the waveform, track dropping on a three-audio-track file and cancel. `rec-core` (`library`) and `cortex-desktop` (`trim`) unit-test names, ranges, copy names, Range headers and the scan.
- **Test-pattern recordings.** Rec's test pattern draws a synthetic picture with a white flash and a beep, so it needs no Screen Recording permission. `engine_smoke` records 3 s at 1080p60 through `MacEngine` and checks the file with ffprobe (H.264, 1920x1080, 60/1, 180 frames) and with an AVFoundation probe. `crates/rec-engine-macos/scripts/selftest.sh` runs Rec's longer checks, including A/V sync.
- **Go live against local servers only.** Never point a test at YouTube, Twitch or Kick. Receive RTMP with `ffmpeg -listen 1 -i rtmp://127.0.0.1:19351/live/test -c copy -f flv out.flv` (ffmpeg 6.1+ also takes enhanced-RTMP HEVC), WHIP with the `whip_sink` example, and stream with `REC_STREAM_KEY=test` and the `live_smoke` example (`--record`, `--replay`, several `--url`). ffmpeg can't listen for RTMPS; put a local TLS terminator in front and set `REC_INSECURE_TLS=1` for its self-signed certificate. Results and the real-platform checklist are in `rec-research/09-go-live-verification.md`.
- **UI logic.** Vitest for React logic, and Playwright against the browser harness on :3002 with the mock engine.
- **Real app.** Tauri WebDriver does not support macOS. For changed UI or runtime behaviour in the real app, use the `evidence-driven-testing` skill and keep the recordings in `.artifacts/<task-name>/`.

Real ScreenCaptureKit capture cannot run in CI because hosted runners cannot grant Screen Recording. CI covers the test pattern only.

## CI

`.github/workflows/desktop.yml` runs on a macOS runner when a change touches `crates/**`, `apps/desktop/**`, `packages/ui/**`, `Cargo.*` or `third_party/**`. It runs fmt and clippy on the crates we own, `cargo test --workspace`, the `engine_smoke` recording, `pnpm --filter desktop check-types`, and an unsigned `tauri build --debug --bundles app`. No signing secrets are configured. `.github/workflows/desktop-windows.yml` does the same on `windows-latest` for `rec-core`, `rec-engine-windows` and `cortex-desktop` (fmt, clippy, tests) and builds the NSIS and MSI installers; it has not run yet. The Linux `ci.yml` job does not build Rust.

## Windows and Linux

`rec-core` has no Apple code on purpose, and the shell reaches OS code only through `src-tauri/src/platform` (`RecorderEngine` and `MediaLibrary` from `rec-core`, plus the shell's `DesktopEngine`, `WindowChrome`, `Hotkeys` and `SystemIntegration`). `EngineState.capabilities` tells the UI what the running engine supports.

- **Windows** builds against `rec-engine-windows` (Windows.Graphics.Capture, Media Foundation, WASAPI). It is type-checked and its logic unit-tested on the Mac, but it has not run on Windows yet. `CORTEX_DEBUG_FRAGMENTED_MP4=1` tries Media Foundation's fragmented (crash-safe) MP4 sink. The first-run script is [Testing the Windows engine](windows-testing.md).
- **Linux** builds against a stub engine that says recording is not available yet.

[Platforms](platforms.md) has the full inventory of macOS touch points, the cross-target build status, the Windows engine's status per capability, and the design for Linux.
