# Desktop recorder

Cortex ships a macOS screen, camera and audio recorder. The capture engine is Rec (rec-rs), imported with its history. The UI is a Tauri 2 app with a React front end that reuses `packages/ui`. This page covers how the pieces fit, where each concern lives, and the rules that differ from the web app.

## The layout

| Folder                    | Job                                                                                                    | May depend on                            |
| ------------------------- | ------------------------------------------------------------------------------------------------------ | ---------------------------------------- |
| `crates/rec-core`         | Platform-neutral settings schema, engine API (`RecorderEngine`, `EngineEvent`), state, settings store. | serde, specta (optional). No Apple code. |
| `crates/rec-engine-macos` | Rec's capture, compose, encode, mixer and live code. Exposes `MacEngine`, which implements `rec_core`. | rec-core, Apple frameworks               |
| `crates/rec-macos-ui`     | Native window behaviour: live preview view, non-activating panels, capture exclusion, levels.          | Apple frameworks, raw-window-handle      |
| `crates/rec-cli`          | The `rec-rs` command-line recorder.                                                                    | rec-engine-macos                         |
| `apps/desktop/src`        | React 19 + Vite + Tailwind 4 surfaces (main, settings, HUD, toasts, countdown, region picker, trim).   | `@starter/ui`, `@tauri-apps/api`         |
| `apps/desktop/src-tauri`  | The Tauri shell (Rust crate `cortex-desktop`): windows, tray, IPC commands.                            | rec-core, rec-engine-macos, rec-macos-ui |
| `third_party/`            | Patched copies of upstream crates. See `third_party/README.md`.                                        |                                          |

The Rust workspace is the root `Cargo.toml` (members `crates/*` and `apps/desktop/src-tauri`). The toolchain is pinned in `rust-toolchain.toml`. `.cargo/config.toml` sets `MACOSX_DEPLOYMENT_TARGET=15.0`, because the engine uses ScreenCaptureKit APIs from macOS 15. The pnpm workspace sees `apps/desktop` as the package `desktop`.

## Request flow

```
React surface (apps/desktop/src/surfaces/*)
   │
   ▼
lib/engine.ts                 useEngine(select?), level sources, connectEngine(). In a plain browser it is the mock engine.
   │
   ▼
ipc/bindings.ts               generated by tauri-specta. Typed commands and the engine://state event.
   │  invoke()
   ▼
Tauri command (src-tauri/src/ipc.rs)        the single IPC checkpoint
   capability allow-list (capabilities/default.json) → serde-typed input → validation
   │
   ▼
rec_core API                  RecorderEngine trait, RecorderSettings, EngineState, EngineEvent
   │
   ▼
MacEngine (rec-engine-macos)  state machine, pacer, compositor, writer, mixer
   │
   ▼
ScreenCaptureKit (screen, system audio) · AVFoundation (camera, mic, file writer) · VideoToolbox (H.264/HEVC)
```

Events travel back the same way. The engine calls its `EventSink`, the shell broadcasts `engine://state`, and `lib/engine.ts` updates the store that `useEngine()` reads.

Video frames never enter the webview. The preview is a native view under a transparent region of the window, so the webview only carries state, settings and levels.

The shell runs `MacEngine` through `src-tauri/src/shell.rs`.

## Live preview

```
MacEngine preview session ──(CVPixelBuffer, ≤30 fps, scaled to the view)──▶ PreviewView sink
                                                                             │
NSWindow (main) ─ contentView ─┬─ PreviewView (AVSampleBufferDisplayLayer, below)
                               └─ WKWebView (drawsBackground = NO, page has a hole)
```

- **Native side.** `src-tauri/src/preview.rs` (`LivePreview`) attaches `rec_macos_ui::PreviewView` to the main window at setup, makes the webview transparent (`make_window_webviews_transparent`) and connects `PreviewView::sink()` to `MacEngine::set_preview_sink`. Both `rec-macos-ui` entry points take a window handle, so the shell has no `unsafe`.
- **Commands.** `set_preview_rect(x, y, w, h, radius)` places the view (CSS px from the webview's top-left) and tells the engine the view's pixel size. `set_preview_enabled(bool)` says whether the page shows the hole. Only the main window may call them (`capabilities/preview.json`).
- **When it runs.** The engine's preview session runs while the hole is shown and the window is visible. Visibility comes from the window's occlusion state, so hiding, minimising, covering the window or moving to another Space stops it. Rec's rule still holds: the replay buffer and streaming keep the engine capturing without a preview. The decision is `should_preview` in `preview.rs` (unit-tested). `CORTEX_DEBUG_PREVIEW_STATS=1` prints each on/off decision with its reason, and 0 fps while the preview is stopped.
- **Events.** Each window is its own WebKit process. `lib/engine.ts` listens per window, the shell sends level events only to visible windows, and progress-only state reaches hidden windows once a second. A hidden page stores that state and renders it only when it is shown again (`lib/visibility.ts`).
- **Render cost.** A visible webview should stay still while recording. Levels (about 30 a second) go to their own store in `lib/engine.ts` (`micLevels`, `systemLevels`), and `LevelMeter` given a `source` toggles segment attributes on an animation frame, with no React render. State events keep the previous object for fields whose content did not change. Window roots use `useEngineCalm()`, which ignores the progress counters, and the clock, bytes, dropped frames and free disk render from the leaves in `components/progress-text.tsx` once a second. Use `useEngine(select, isEqual)` for new views instead of reading the whole state. Avoid `backdrop-filter` and large repainting effects over the preview hole.
- **Frame size and rate.** The writer sends at most 30 preview frames a second. The engine scales each one with Rec's Metal Lanczos scaler (`FrameScaler`) to the view's pixel size, at most 1920 wide, before the sink. Low-power preview halves the rate to 15.
- **React side.** In the Tauri main window `PreviewStage` renders an empty box instead of `MockScreen` and reports its rect through `useNativePreviewHole` (`lib/native-preview.ts`): ResizeObserver, window resize and display scale changes. Nothing above the native view may paint, so `html[data-preview-hole]` makes html, body and the window roots transparent; the hole's box-shadow paints the dark stage around it, and a fixed backdrop behind everything paints the page around the stage. The camera overlay stays a React drag handle above the video (the engine draws the camera itself). The browser harness still renders `MockScreen`.
- **Own windows stay out of recordings.** The shell calls `rec_engine::screen::require_self_exclusion(true)`. If ScreenCaptureKit doesn't list the app, the engine looks once more after refreshing and then fails the capture with a clear error, rather than recording our own windows. The CLI leaves it off: it has no windows.

### Perf and self-test hooks

The shell reads these at launch (never set in normal use): `CORTEX_DEBUG_DATA_DIR` (settings folder), `CORTEX_DEBUG_TEST_PATTERN=1` (record Rec's test pattern, no Screen Recording grant needed), `CORTEX_DEBUG_RECORD_SECS=N` (record N s after launch, print the path, quit), `CORTEX_DEBUG_HIDE_MAIN=1`, `CORTEX_DEBUG_FRONT=1` (keep the main window on top and on every Space, full-screen ones included, so the preview keeps running; a Space switch or Mission Control by someone at the Mac otherwise stops it, which is what cut short idle perf runs), `CORTEX_DEBUG_PREVIEW_STATS=1` (print the preview frame rate) and, in debug builds, `CORTEX_DEBUG_OPEN=menubar|region|settings|onboarding|trim` (open that window 2 s after launch). `scripts/desktop/perf-compare.sh` uses them to compare CPU, memory and frame counts with Rec.app's `rec-rs record --test-pattern`, and marks an idle preview-on run invalid when any 5 s preview window drops under 29 fps.

| Concern                                             | Lives in                                                                                    |

`bindings.ts` plays the role `RouterOutputs` plays on the web. If a TypeScript type for a setting or state field is wrong, fix the Rust type in `rec-core` and regenerate.

```

pnpm --filter desktop tauri dev                  the real app with hot reload
pnpm --filter desktop tauri build --debug        debug .app in target/debug/bundle/macos
pnpm --filter desktop check-types                TypeScript check
pnpm --filter desktop ipc:bindings               regenerate src/ipc/bindings.ts from the Rust commands

cargo clippy --no-deps -p rec-core -p cortex-desktop -p rec-macos-ui -- -D warnings

cargo run --release -p rec-engine-macos --example engine_smoke   test-pattern recording + ffprobe check
```

The design harness runs every surface against `lib/mock-engine.ts`. Use it for design review and Playwright. It needs no Rust build.

After changing a command, an event or any type it carries, run `ipc:bindings` and commit the new `bindings.ts` with the Rust change. Adding a command also means adding it to `COMMANDS` in `build.rs` and granting `allow-<command>` in the capability file, or the webview cannot call it.

## Windows are built on demand

Only the main window exists at launch. Every other window in `tauri.conf.json` (settings, onboarding, trim, menu bar panel, HUD, toasts, countdown, region picker) has `"create": false`. Each window is its own WebKit WebContent process (40 to 200 MB, plus CPU while it animates), so building them all at launch cost about 1 GB and, while recording, about 3% of a core per hidden window.

- **Build.** `windows::ensure(app, label)` returns the window, building it from its config entry first if needed. Every path that shows a window goes through it: `open_window` (settings, onboarding, trim; the webview can no longer find windows by label), `open_floating`, the tray click, and the engine-driven countdown, HUD and toasts. Floating windows get their native behaviour in `floating::on_created` before they are shown.
- **Destroy.** `windows::reap` runs every 5 s and destroys a lazy window that has been hidden for 30 s, so its WebContent process exits. It keeps the HUD and menu bar panel while recording, the countdown while it runs or while it is warm, and the toasts window until it has delivered what it holds.
- **Countdown latency.** A countdown window built when the countdown starts renders about 130 to 150 ms later (debug build). To avoid that delay, the countdown is built ahead of time whenever the main window gets focus and a countdown is set, and it stays warm while the main window is shown.
- **Toasts.** Toasts go through the shell, not straight to the toasts window, because that window may not exist yet. The floating observer turns `recording-finished`, `replay-saved` and `error` into toasts, other windows call `push_toast`, and the shell holds them until the toasts window calls `window_ready` after its first render. Every window calls `window_ready`, and the shell logs how long the window took from creation to that point.
- **Hidden pages idle.** `lib/visibility.ts` mirrors `document.hidden` onto `html[data-hidden]`, which pauses every CSS animation (`styles.css`), and `engine.ts` defers state renders until the page is visible. WebKit reports an ordered-out or fully covered window as hidden (checked with a debug probe: the countdown and HUD flip to `hidden` when the shell hides them and back when it shows them).

## Camera track

With **Save camera as separate track** on (`cameraTrack`, Settings → Camera) and a camera in the recording, the engine also records the raw camera (`rec record --camera-track file|sidecar`, `writer::CameraTrack`). The burned-in overlay stays in the main track either way.

- **Where it goes.** A `.mov` gets a second video track, in one alternate group with the main track (main is the default), so QuickTime and AVPlayer show the composite and editors see both. An `.mp4` gets a sidecar `<name>.camera.mov` next to it instead, because many editors ignore a second video track in MP4. `Recording.hasCameraTrack` is true only for the in-file track (an `.mp4`'s camera is in the sidecar).
- **Unmirrored.** The track holds the frames as the camera delivers them. Mirroring is a display choice applied by the compositor to the overlay only.
- **Timeline.** The pacer appends the newest camera frame on every main-track slot, with the main track's timestamp: CFR at the output fps, same start, same pause cuts, same end (`endSessionAtSourceTime` trims both). A 30 fps camera on a 60 fps grid repeats each frame, which costs almost nothing in H.264/HEVC. The sidecar starts its session at the same host time, so it lines up at 0 with the main file.
- **Encoding.** Same codec as the main track (ProRes main gives a ProRes camera track), at the camera's size, with a bitrate sized for 30 real frames (`writer::camera_video_spec`). Both files are fragmented every 2 s, so a crash leaves the camera playable up to the last fragment too.
- **Resolution.** `cameraResolution` (720p or 1080p) caps the capture format. `camera::pick_format` takes the largest device format at or under that height (24 fps or faster), so a 720p-only camera falls back to 720p. The frames are delivered at exactly that size, and a running camera is reused for a recording only when it was opened at the same cap (the preview reopens when the setting changes).
- **Camera-only scene.** The track is recorded there too: the scene can switch live, and the track keeps the camera's native size.
- **Cost.** Measured 2026-11-03 on the FaceTime HD camera at 1080p, test pattern at 1080p60 H.264, 20 s window: 50.3% CPU with the track, 48.2% without (about +2 points), and about 9.5 Mb/s more file. `writer::tests::camera_track_follows_the_main_timeline` checks length, frame count and pause cuts for both the .mov track and the .mp4 sidecar.

## Floating windows

The HUD, toasts, countdown, region picker and menu bar panel are built on demand (see above). `src-tauri/src/floating.rs` owns their behaviour:

- **Native panel behaviour.** When one is built, `rec_macos_ui::configure_floating_window` gives it its `FloatingKind` level (menu bar panel highest, then countdown and toasts, region picker, HUD), puts it on all Spaces and over full-screen apps, makes it non-activating (`_setPreventsActivation:` on tao's window) and sets `sharingType = none`. The countdown also ignores mouse clicks. The safe wrappers take the window handle, so the shell has no `unsafe`.
- **Driven by the engine.** Every outbound event passes through `floating::observer` before it reaches the webviews. The countdown window shows centred on the main display while the status is `countdown`. The HUD shows while recording or paused if `settings.showHud` is on, the user did not hide it, and the main window is not frontmost. Its bottom-centre is remembered per display in `hud-positions.json` (Application Support) and kept inside the visible area.
- **Toasts have one owner.** The toasts window builds the queue from `engine://recording-finished`, `engine://replay-saved` and `engine://error`, which the shell sends to it (and holds until it is ready). Other windows send their toasts (failed commands) through `push_toast`, which reaches it as `ui://toast`. It shows itself top-right under the menu bar on the display under the cursor, and hides when the queue is empty.
- **Sized to content.** In a window, a floating surface renders only its card (`useWindowed()` from `lib/floating.ts`). `FittedHost` in `app/tauri-window.tsx` measures it and calls `fit_floating`, which keeps the HUD's bottom-centre and the countdown's centre in place. The browser harness keeps the fake desktop layout.
- **Opening and closing.** `open_floating` places the menu bar panel under the status item and the region picker over the full display under the cursor (one overlay per display is still to do). `hide_floating` closes the calling window; the menu bar panel also closes on blur and Esc, the region picker on confirm or cancel. A hidden HUD comes back from the panel menu ("Show recording HUD") or on the next recording.
- **Global hotkeys** use Carbon (`rec_engine::hotkey`), which needs no Accessibility permission: ⇧⌘R starts, cancels the countdown, or stops; ⇧⌘S saves the replay and is registered only while the replay buffer is on; Esc is registered only during the countdown and cancels it.
- **Main window and quit.** Closing the main window hides it; the app stays in the menu bar and a Dock click reopens it. Quit finalizes an active recording and flushes settings before the process ends (`src-tauri/src/quit.rs`). An exit request (tray Quit, `AppHandle::exit`, the debug recording run, SIGTERM or SIGINT) is held back while a `quit` thread runs `Shell::shutdown`, then that thread exits, so the event loop keeps running while the file is written. ⌘Q from the app menu skips `ExitRequested`; `RunEvent::Exit` runs the same shutdown on the main thread. `MacEngine::shutdown` waits at most 500 ms for its ticker thread and then finalizes without it.

Screenshots cannot see these windows, because they are excluded from sharing. To check them, run a debug build with the test pattern:

```
CORTEX_DEBUG_TEST_PATTERN=1 CORTEX_DEBUG_RECORD_SECS=6 CORTEX_DEBUG_HIDE_MAIN=1 CORTEX_DEBUG_CAPTURABLE=1 \
  target/debug/bundle/macos/Cortex.app/Contents/MacOS/cortex-desktop
```

It keeps its settings and recordings in a temporary folder, starts one recording with a 3 s countdown, and with `CORTEX_DEBUG_CAPTURABLE=1` lets `screencapture` see the floating windows. Release builds ignore these variables.

## Permissions

macOS privacy grants (TCC) are read and requested by `rec_engine::tcc`. The app never runs `tccutil reset` (that wiped grants the user had given) and never re-launches its own executable to ask; both stay in the `rec` CLI's `permissions --request` path only.

- **Run with what is granted.** `rec_core::sources::plan_sources` decides per source from the scene, the mic switch and the grants. A missing camera or microphone grant drops that source from the preview and recordings; it does not stop them. Only a source the scene cannot do without blocks it: the screen for Screen and Screen + Camera, the camera for Camera only. The camera-only scene runs without a Screen Recording grant (the camera's frames drive the clock, and the mic uses AVCapture). The CLI keeps its strict check (`record::check_permissions`).
- **Say what is missing.** The preview shows "Camera needs permission · Allow" where the overlay goes and "Microphone needs permission · Allow" in the mixer strip. Empty camera and mic menus offer "Allow camera access…" / "Allow microphone access…". Allow shows the system prompt when macOS has never asked, and opens System Settings otherwise (macOS asks only once).
- **Starting a recording** asks first for an undecided microphone (and camera, in camera scenes), waiting for the answer. A source that stays missing is left out, with a warning toast.
- **`request_permission`** shows the prompt for camera and microphone (`requestAccessForMediaType`, answered off the main thread) and calls `CGRequestScreenCaptureAccess` for the screen, which lists Cortex in System Settings. It returns the resulting state.
- **`check_permissions`** is cheap and polled once a second by onboarding. A running process keeps the Screen Recording answer it had at launch, so when this process still sees no grant, the command asks a new process of the same app (`cortex-desktop --cortex-screen-preflight`). If that one sees the grant, `screenNeedsRelaunch` is set and onboarding shows **Reopen Cortex** (`relaunch`, refused while recording).
- The engine re-reads grants about once a second. A change re-lists cameras and mics and rebuilds the preview, so a grant takes effect without a restart. Devices are also listed on the engine's first tick.
- Usage strings (`NSCameraUsageDescription`, `NSMicrophoneUsageDescription`, `NSScreenCaptureUsageDescription`) live in `src-tauri/Info.plist` and must be in the built bundle, or macOS refuses to prompt.

To check the missing-permission paths on a Mac where everything is granted, set `CORTEX_DEBUG_WITHHOLD=camera,microphone` (grants then read as never asked). Launch test builds with `open -n -a <app> --env ... --stdout <log> --stderr <log>`: run straight from a terminal, macOS charges TCC to the terminal app and the grants you see are the terminal's.

## Dev signing identity

macOS ties Screen Recording, Camera and Microphone grants (TCC) to the app's code signature. An ad-hoc signature changes on every build, so each rebuild looks like a new app and macOS asks again. A stable self-signed certificate keeps the grants across rebuilds.

This Mac has a self-signed code-signing certificate called **Cortex Dev Signing** in the login keychain. Sign local builds with it:

```
APPLE_SIGNING_IDENTITY="Cortex Dev Signing" pnpm --filter desktop tauri build --debug
```

To create one on another Mac, open Keychain Access, choose Certificate Assistant, Create a Certificate, and pick type "Code Signing". `security find-identity -p codesigning` should then list it. It shows as not trusted, which is fine for local signing.

This identity is for development only. It cannot pass Gatekeeper on another machine. Public builds need a Developer ID certificate and notarization, which come later. Never commit the certificate or its private key, and never put it in CI.

## The Swift 6.4 cryptokit patch

The root `Cargo.toml` points at it through `[patch.crates-io]`.

Remove the copy and the patch entry once upstream ships a fix. `third_party/README.md` has the details.

## Security rules for the desktop app

There is no server in the recorder yet, so the tRPC procedure builder does not apply. These rules take its place:

- **One IPC checkpoint.** Every webview call is a command in `src-tauri/src/ipc.rs`. Each window gets only the commands its capability lists. No shell, fs, http or other plugin is enabled for the webview.
- **Validate in Rust.** Commands take serde types from `rec-core`. Rust checks ranges, enums and paths before the engine sees them. Settings forms in React also validate with Zod, as on the web.
- **No secrets over IPC.** Stream keys live in the macOS Keychain. The webview can set or remove a key but only ever reads back a `keyStored` flag. Never log a key.
- **No remote content.** The CSP in `tauri.conf.json` allows only `'self'`, IPC, and `blob:`/`data:` media. Fonts and assets are bundled. Do not add CDN URLs or `withGlobalTauri`.
- **Writes stay in the output folder.** The engine writes recordings only under the chosen output directory, and the settings store only under the app's Application Support folder.
- **Minimal entitlements.** `Entitlements.plist` grants camera and audio input only. Add one only with a stated reason.
- **Hidden from recordings.** HUD, toasts, countdown, the region picker and the menu bar panel must never appear in a capture. The engine's `SCContentFilter` excludes the whole app, and `rec-macos-ui` sets `sharingType = none` so other apps' screenshots miss them too.

## Rust rules

- No new `unsafe` outside `rec-engine-macos` and `rec-macos-ui`. Every `unsafe` block has a `// SAFETY:` comment that says why the call is sound.
- New crates must pass `cargo fmt --check` and `cargo clippy -- -D warnings`. CI enforces this for `rec-core` and `cortex-desktop`. The imported Rec crates keep their upstream style for now, so subtree pulls stay clean.
- **Never block on the main thread from engine or background threads.** Engine events reach `ipc::emitter` and `floating::observer` on the engine's ticker and writer threads, and at quit the main thread waits for those threads. Any `WebviewWindow` getter (`is_visible`, `outer_position`, `scale_factor`, ...) or `run_on_main` from `rec_macos_ui` called off the main thread waits for the main thread: that deadlocked quit. From those threads, read cached state (`ipc::VisibleWindows`) and hand window work to `AppHandle::run_on_main_thread` without waiting for it. The same applies to anything the main thread may join.
- Errors cross IPC as `rec_core::EngineError`, never as panics. Do not `unwrap()` on input that came from the webview.
- The TypeScript rules in `CLAUDE.md` still apply to `apps/desktop/src`.

## Testing

- **Rust unit tests.** `cargo test --workspace`. `rec-core` covers the state machine, settings migration and the store. The imported engine keeps Rec's tests.
- **Quit regressions.** `ipc::tests` reproduces the quit deadlock in miniature (a wait on the main thread from the ticker while the main thread joins it) and checks the visibility registry gets through. `crates/rec-engine-macos/tests/shutdown_blocked_sink.rs` holds the ticker inside the event sink and requires `shutdown` to return and leave a playable file.
- **Test-pattern recordings.** Rec's test pattern draws a synthetic picture with a white flash and a beep, so it needs no Screen Recording permission. `engine_smoke` records 3 s at 1080p60 through `MacEngine` and checks the file with ffprobe (H.264, 1920x1080, 60/1, 180 frames) and with an AVFoundation probe. `crates/rec-engine-macos/scripts/selftest.sh` runs Rec's longer checks, including A/V sync.
- **UI logic.** Vitest for React logic, and Playwright against the browser harness on :3002 with the mock engine.
- **Real app.** Tauri WebDriver does not support macOS. For changed UI or runtime behaviour in the real app, use the `evidence-driven-testing` skill and keep the recordings in `.artifacts/<task-name>/`.

Real ScreenCaptureKit capture cannot run in CI because hosted runners cannot grant Screen Recording. CI covers the test pattern only.

## CI

`.github/workflows/desktop.yml` runs on a macOS runner when a change touches `crates/**`, `apps/desktop/**`, `packages/ui/**`, `Cargo.*` or `third_party/**`. It runs fmt and clippy on the crates we own, `cargo test --workspace`, the `engine_smoke` recording, `pnpm --filter desktop check-types`, and an unsigned `tauri build --debug --bundles app`. No signing secrets are configured. The Linux `ci.yml` job does not build Rust.

## Windows later

`rec-core` has no Apple code on purpose. A future `rec-engine-windows` (Windows.Graphics.Capture, Media Foundation, WASAPI loopback) would implement the same `RecorderEngine` trait, and the shell would pick the engine with `#[cfg(target_os)]`. The React surfaces and the generated bindings would not change.

Expect to rework the macOS-only parts: `rec-macos-ui` (panels, capture exclusion), the Keychain store, TCC permission flows, `macOSPrivateApi` transparent windows, and the `.cargo/config.toml` deployment target. Keep new platform-specific code behind a crate or `cfg` boundary so that work stays contained.
