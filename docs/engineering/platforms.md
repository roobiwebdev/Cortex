# Platforms: macOS, Windows (untested), Linux next

Cortex records on macOS. A Windows engine is written but has not run on Windows yet. This page covers the seam that lets Windows and Linux engines plug in without touching the React surfaces, the IPC bindings or the shell's logic: what the interface is, every place the shell used to call macOS code, what builds for other targets today, the Windows engine as built, and the plan for Linux.

## The interface

The contract is split in two, by what it depends on.

| Where                                        | What                                                                                                                                        | Why there                                                                                                                                                    |
| -------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `crates/rec-core/src/api.rs`                 | `RecorderEngine`: record, pause, stop, discard, replay, live, devices, permissions, preview on/off and size, device watching, stream keys.  | Only `rec-core` types (settings, state, events). An engine crate implements it without knowing about Tauri, as `MacEngine` does.                             |
| `crates/rec-core/src/platform.rs`            | `PlatformCapabilities` (inside `EngineState`), `EngineOptions`, `MediaLibrary` (+ `MediaInfo`, `ExportOptions`, `MediaError`), `Secrets`.   | Same reason. Capabilities are sent to the UI, so they belong with the other IPC types; media and secrets are plain data in and out.                          |
| `apps/desktop/src-tauri/src/platform/mod.rs` | `DesktopEngine` (`RecorderEngine` + `attach_preview`), `PreviewSurface`, `WindowChrome`, `Hotkeys`, `SystemIntegration`, and the selectors. | These take a Tauri `WebviewWindow`, run on the app's main thread or act on the app process. Only the shell uses them, so a separate crate would add nothing. |
| `src-tauri/src/platform/macos.rs`            | The macOS implementation: forwards to `rec-engine-macos` and `rec-macos-ui`.                                                                | Same calls, same order, same messages as before the split.                                                                                                   |
| `src-tauri/src/platform/windows.rs`          | The Windows implementation: forwards to `rec-engine-windows` (engine, `win::shell`, `win::media`) and Explorer.                             | Same traits; the Win32 `unsafe` stays in the engine crate.                                                                                                   |
| `src-tauri/src/platform/unsupported.rs`      | The Linux stub: builds, lists nothing, answers "Recording on Linux is not available yet".                                                   | The shell compiles for every target, so engine work starts from a building app.                                                                              |

`platform/mod.rs` picks the implementation once with `#[cfg(target_os = ...)]`: `macos.rs`, `windows.rs`, else the stub. Everything else calls `platform::open_engine`, `platform::chrome()`, `platform::hotkeys()`, `platform::system()` and `platform::media()`. `Shell` holds a `Box<dyn DesktopEngine>`. No shell module except `platform/macos.rs` names `rec_engine` or `rec_macos_ui`, and both crates are `[target.'cfg(target_os = "macos")'.dependencies]` of `cortex-desktop`. Likewise only `platform/windows.rs` names `rec_engine_windows`, a `[target.'cfg(windows)'.dependencies]` entry.

**Why not a new `rec-platform` crate?** `rec-core` already is the platform-neutral crate: it holds `RecorderEngine`, has no Apple code and only depends on serde. A second neutral crate would split one contract over two places. The window-level traits cannot go into `rec-core` without pulling in Tauri or `raw-window-handle`, and the only caller is the shell, so they live there.

**Adding a platform.** Write an engine crate (`crates/rec-engine-windows`, `crates/rec-engine-linux`) that implements `RecorderEngine`, `MediaLibrary` and `Secrets`. Add `platform/windows.rs` (or `linux.rs`) next to `macos.rs` that implements `DesktopEngine`, `WindowChrome`, `Hotkeys` and `SystemIntegration`, then switch the `cfg` in `platform/mod.rs` from the stub to it. Nothing else in the shell changes.

### Capabilities

`PlatformCapabilities` says what the running engine can do, so the UI can hide or explain a feature instead of failing when it is picked. It is part of `EngineState` (`state.capabilities` in React). Today the UI uses it in four places: HEVC and ProRes appear only when `capabilities.hevc` / `capabilities.prores` are true (a stored choice stays listed so the select never goes blank); the Container control offers MOV only with `movContainer`; the camera-track switch and chip show only with `cameraTrack`; and the main window cuts its transparent preview hole only when `preview` is `native` (otherwise a placeholder fills the stage).

| Field                              | macOS     | Windows (built, untested)                     | Linux Wayland (plan)                 | Linux X11 (plan)   |
| ---------------------------------- | --------- | --------------------------------------------- | ------------------------------------ | ------------------ |
| `recording`                        | yes       | yes when WGC is supported (Windows 10 1903+)  | yes                                  | yes                |
| `displayCapture` / `regionCapture` | yes / yes | yes / yes (crop)                              | yes / yes (crop)                     | yes / yes          |
| `windowCapture`                    | yes       | yes                                           | yes, portal-picked                   | yes, portal-picked |
| `appCapture`                       | yes       | no (an app target records its largest window) | no                                   | no                 |
| `sourcePicker`                     | `app`     | `app`                                         | `system`                             | `system`           |
| `systemAudio`                      | yes       | yes (WASAPI loopback)                         | yes (sink monitor)                   | yes                |
| `perAppAudio`                      | yes       | no (process loopback later, Windows 11)       | no at first                          | no at first        |
| `captureExclusion`                 | yes       | yes on build 19041+ (Windows 10 2004)         | no                                   | no                 |
| `globalHotkeys`                    | yes       | yes                                           | only with the GlobalShortcuts portal | yes                |
| `hevc` / `prores`                  | yes / yes | if an HEVC encoder MFT exists / no            | if VA-API/NVENC has HEVC / no        | same as Wayland    |
| `preview`                          | `native`  | `fallback` (placeholder; no frames sent yet)  | `fallback`                           | `fallback`         |
| `liveStreaming` / `replayBuffer`   | yes / yes | no / no                                       | later                                | later              |
| `quickTrim`                        | yes       | no (inspect and Recycle Bin only)             | yes (GStreamer)                      | yes                |
| `movContainer`                     | yes       | no (MP4 only)                                 | no                                   | no                 |
| `cameraTrack`                      | yes       | no                                            | later                                | later              |

The Linux stub reports everything off. `movContainer` and `cameraTrack` were added with the Windows engine; expect more fields as engines arrive. Outside macOS the settings default to MP4 and `~/Videos/Cortex` (`rec_core::settings::DEFAULT_CONTAINER`, `DEFAULT_OUTPUT_DIR`).

```sh

# Type-check shim only: answers like llvm-rc and writes an empty resource file.

while [ $# -gt 0 ]; do if [ "$1" = "/fo" ]; then : > "$2"; fi; shift; done
```

### How it is put together

| Part            | File                                                                                      | What it does                                                                                                                                                                                                                                          |
| --------------- | ----------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| State machine   | `src/engine.rs`                                                                           | `Engine<B: Backend>` implements `RecorderEngine`: same transitions (`rec_core::api::transition`), events, 30 Hz ticker, "events after the lock" rule and bounded shutdown as `MacEngine`. `WindowsEngine = Engine<win::WinBackend>`.                  |
| Pure rules      | `timeline.rs`, `audio.rs`, `plan.rs`, `overlay.rs`, `devices.rs`, `caps.rs`, `pattern.rs` | CFR slot grid and pause cuts, mixer/resampler/faders/limiter, codec/size/bitrate from `rec_core::output`, camera overlay geometry and mask, device-list rules, capabilities, test pattern. Ported from `rec-engine-macos` where a rule existed there. |
| Windows backend | `src/win/*` (`cfg(windows)`)                                                              | Devices, capture, compositor, encoder, audio, camera, Credential Manager, the shell helpers and the media library.                                                                                                                                    |
| Shell adapter   | `apps/desktop/src-tauri/src/platform/windows.rs`                                          | `DesktopEngine`, `WindowChrome`, `Hotkeys`, `SystemIntegration`, `MediaLibrary` forwarding to the crate. No `unsafe` in the shell.                                                                                                                    |

A recording runs two threads. The **video pacer** polls the Windows.Graphics.Capture frame pool for the newest frame, copies the target's crop onto a BGRA canvas (`CopySubresourceRegion`), draws the camera overlay as one textured quad, then scales the canvas to the output size and converts it to NV12 with `ID3D11VideoProcessor` into a ring of 8 textures. Each slot of the constant-frame-rate grid on the QPC clock gets a frame: a new one when the picture changed, the last one again when it didn't (or when the pacer woke late). The timeline starts at the first captured frame. The **audio writer** takes WASAPI buffers (QPC-stamped), applies the faders, places them on the mix and stem timelines (`audio::Mixer`), cuts the pauses (`timeline::audio_keep`), keeps each track gap-free (`TrackClock`) and writes AAC. Both write to one `IMFSinkWriter` behind a mutex, with throttling off and the video thread bounding its own backlog (it repeats a frame rather than overwrite a ring texture the encoder may still read).

### Replay buffer and Go live: can the macOS code be reused?

Not as it is. In `rec-engine-macos/src/live`, the RTMP client (`rtmp.rs`) is mostly plain Rust over `TcpStream` and `native-tls` (both portable), but it reads frame sizes from a `CMFormatDescription`, and the packets it sends come from `video.rs` (VideoToolbox) and `audio.rs` (AudioToolbox). The replay writer (`replay.rs`) is AVFoundation, the WHIP client depends on `str0m` with Apple crypto, and the key store is the Keychain. A Windows version needs: the RTMP/FLV muxing split from CoreMedia types into a neutral crate, a second Media Foundation encoder session for the live bitrate (or the recording's packets taken from an `IMFTransform` instead of the sink writer), a replay ring of encoded packets written with a sink writer, and `str0m` with a portable crypto feature for WHIP. That is a separate piece of work.

### Limits worth knowing

- **App capture** records one window, not the app.
- **Window resize**: the frame keeps the size the window had at the start.
- **The preview** is a placeholder; Cortex shows no live picture on Windows yet.
- **Hotkey labels** in the UI still read ⇧⌘R and ⇧⌘S. They are written out in about 15 places (menubar panel, HUD, record bar, sources sidebar, live settings, onboarding) with no shared label function, so a per-platform label needs a small helper first (for example `shortcutLabel("record")` reading `capabilities.os`).
- **Title bars**: `titleBarStyle: "Overlay"` is macOS-only, so Windows shows its own title bar above the app's.

New crate `crates/rec-engine-linux`. Wayland is the default session on Ubuntu, Fedora and most distros now, so design for the portal first and treat X11 as a bonus.

**Wayland limits that change the product, not just the engine:**

- The app cannot list windows or apps, so the Area/Window/App pickers become one "Choose what to record" button that opens the system picker (`sourcePicker: system`).
- No app capture, and nothing excludes our own windows from a portal capture. The HUD and toasts will be recorded if they sit on the captured screen; hide them while recording on Wayland, or warn.
- Clients cannot place their own windows. `set_position` is ignored, so the HUD position, the toasts' top-right spot, the countdown centre and the full-screen region picker overlay do not work as on macOS. Layer-shell would fix it but Tauri does not expose it. The region picker needs a portal-first redesign (pick a monitor in the portal, then crop inside our own window).
- Always-on-top and "on all workspaces" are compositor hints at best.

## Risks

- **Mac regressions from this split.** The macOS adapter forwards one-to-one, and the full test suite, the shell's record test and a release-bundle recording pass (below). The remaining risk is in code paths the tests do not drive: floating-window setup, hotkeys and the preview view. Those calls kept their order; only the path to them changed.
- **GStreamer licensing.** `x264enc` (gst-plugins-ugly) is GPL. Loading the distro's plugin at run time is fine; bundling it in an AppImage makes that bundle GPL-encumbered. Prefer VA-API/NVENC with `openh264` as the software fallback.
- **H.264/HEVC patents.** Using the OS or GPU encoders (Media Foundation, VA-API, NVENC) puts the licence on the vendor. Shipping our own software encoder does not.
- **Wayland UX** (above): window placement and capture exclusion are the big gaps, and they affect the HUD, toasts, countdown and region picker.
- **Windows HEVC** depends on the GPU and on the HEVC Video Extensions for playback; the encoder may exist while the user's player cannot play the file.
- **The Windows engine has never run.** It type-checks against the `windows` crate's real signatures, but behaviour that only shows at run time is unproven: the video processor accepting BGRA in and NV12 out on the user's GPU, the sink writer taking D3D11 NV12 textures with three AAC streams, `AUTOCONVERTPCM` on loopback, the source reader's RGB32 conversion for the user's camera, the HLSL compiler (`d3dcompiler_47.dll`) being present, and `SetWindowDisplayAffinity` succeeding from a non-UI thread. Each has a fallback or a clear error, and the test script covers each.
- **Windows A/V sync** rests on Windows.Graphics.Capture's `SystemRelativeTime` and WASAPI's QPC position sharing the QPC clock (both documented as such). Measure it with the clap test in the script before trusting it.
- **Encoder backlog on Windows.** Throttling is off (to avoid a cross-stream deadlock in the shared sink writer), so the video thread watches `MF_SINK_WRITER_STATISTICS` and repeats a frame rather than overwrite a texture still queued. An encoder slower than real time therefore shows as dropped frames, as on macOS, but it is untested.
- **Crash safety on Windows.** A plain MP4 is lost if the app dies mid-recording (macOS writes fragmented files). The fragmented sink is opt-in until it is checked with all tracks.
- **Camera-only cost on Windows.** The overlay is drawn on the CPU per camera frame; at 1080p full frame that is a few million pixels 30 times a second. Fine for a bubble, worth measuring for the camera-only scene.
- **Preview cost.** A fallback preview through the webview costs CPU that macOS avoids. Cap it at 15 fps and a small size, and stop it whenever the window is hidden, as `should_preview` already does.
- **Cross-building.** Neither Windows nor Linux bundles can be produced on this Mac. Each needs its own machine or CI runner.
- **Rec upstream.** `rec-engine-macos` gained a small Cortex-specific diff (capabilities, trait forwarding, the media types moved to `rec-core`, `Keychain` as `Secrets`). Keep it in mind when pulling Rec updates.

## Testing on the real Windows and Linux PCs

The user has one Windows PC and one Linux PC. These steps work for the user or for an agent with a shell on that machine (SSH, or a terminal it drives).

**Windows 11 (x64).** Follow [Testing the Windows engine](windows-testing.md): prerequisites, build and unit tests, a test-pattern recording checked with `ffprobe`, then a checklist for each capture target, the audio tracks, the camera, pause, hotkeys and our windows staying out of recordings, and how to collect logs.

**Linux (Ubuntu 24.04 or Fedora, Wayland session).**

1. Install Tauri's prerequisites. Ubuntu: `sudo apt install build-essential curl wget file libssl-dev libxdo-dev libwebkit2gtk-4.1-dev libayatana-appindicator3-dev librsvg2-dev`. Fedora: `sudo dnf install webkit2gtk4.1-devel openssl-devel libxdo-devel libappindicator-gtk3-devel librsvg2-devel` plus the C toolchain. Later, for the engine: GStreamer dev packages (`libgstreamer1.0-dev libgstreamer-plugins-base1.0-dev gstreamer1.0-plugins-bad gstreamer1.0-vaapi`) and `libpipewire-0.3-dev`.
2. Rust through rustup, Node 22 + pnpm, then `pnpm install`.
3. `cargo check -p cortex-desktop` first: this is the check this Mac could not finish.
4. Then `cargo test -p rec-core`, `cargo clippy --no-deps -p rec-core -p cortex-desktop --all-targets -- -D warnings` and `pnpm --filter desktop tauri dev` (the stub opens with no devices and says recording is not available yet). Note the session type (`echo $XDG_SESSION_TYPE`) and desktop (`echo $XDG_CURRENT_DESKTOP`) with every result.
5. Bundles: `pnpm --filter desktop tauri build --bundles deb,appimage` once a `tauri.linux.conf.json` exists.
